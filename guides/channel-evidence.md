# API 渠道怎么核验：报价、路由、能力样本与真实账单

[English](channel-evidence.en.md) · [服务选型](../README.md) · [成本核算](cost-comparison.md) · [会员共享](member-session-sharing.md)

核验一个渠道，先明确要判断什么，再找能回答这个问题的记录。模型名、一次画图、HTTP 200、供应节点数量分别提供不同信息，不能相互替代。

资料日期：**2026-10-09**。本文由 TokenDos 运营方维护，方法适用于本目录所有服务。这里没有新增调用实测、模型身份认证或性能排名；下面的场景是核验方法示例。

## 先把结论与证据对应起来

| 想判断的问题 | 需要核对的证据 | 仅有这些还不够 |
| --- | --- | --- |
| 我的任务是否便宜 | 同币种、同单位的报价；缓存规则；全部尝试的扣费、实际使用的优惠与已确认退款；成功任务数 | 首页最低价、充值赠送比例、某次请求费用 |
| 请求去了哪个渠道 | 请求时的选择、每次尝试报告的节点与路由、回退记录及其来源 | 请求填写的模型名、所用客户端名称 |
| 是否用了共享会员 | SESSION 选择和当时的可用供给；对应任务的供应端、执行记录与扣费 | 共享教程、Agent 聊天成功、API 节点数量 |
| 是否适合我的工作 | 自己的任务、事先确定的完成标准、结果与失败记录 | 一张鹈鹕图、一个通用测评分数 |
| 是否持续可用 | 明确时间窗口、总尝试数、失败数、节点变化与业务完成数 | HTTP 成功率、一次成功调用、供应商口头承诺 |
| 数据由谁处理 | 当前的数据处理条款、实际执行路径、平台及供应方可访问范围 | 凭据留在本机、支持官方客户端、某个隐私标签 |

平台报告的路由字段可以用于追踪和排障，仍属于该平台提供的记录。返回的 `model` 字段或节点标签本身不能认证上游模型身份；未取得可验证的上游来源时，把身份结论保留为未确认。

## 保留三类来源

**公开文档**说明平台宣称支持什么、允许怎样使用、如何计费。记录 URL、日期、适用协议与限制；页面日后变化时，仍能解释当时的选型依据。

**平台公开记录**展示平台记录的样本或统计。保留节点、时间、提示词、设置、成功和失败状态，核对分母与覆盖范围。它们有观察价值，独立性取决于记录产生与公开的方式。

**自己的调用记录**把具体任务与用量、账单、结果对应起来。把重试和失败也纳入；用相同条件复查时，结论只覆盖实际记录的节点、任务和时间窗口。自行复查也不能凭输出风格单独证明模型身份。

## 两个容易得出过强结论的场景

### 看到了好看的鹈鹕图

可以得出的结论是：该记录中的节点在给定时间、提示词和设置下产生了这个结果。先确认记录新旧、是否与准备使用的节点相同，以及其他结果是否使用了不同变体。

如果自己需要代码修改，还要用有明确完成标准的代码任务评价；需要工具调用，就保留工具参数、执行结果与最终任务结果。画图能力与这些需求可以同时观察，不能从一次画图推导全部能力。

TokenDos 的[鹈鹕公开结果](https://www.tokendos.com/api/tokendos/pelican/latest?modelName=claude-opus-4-6)提供节点样本，是其透明度的具体亮点。在线测试会消耗额度；这里没有付费发起新测试，也没有把公开样本当成独立认证。

### 在 Agent 中完成了聊天

先查实际路由：这次尝试报告的是 API 还是 SESSION？有无回退？执行在哪个供应端？无法取得这些信息时，只记录“聊天完成，交付模式未确认”。

TokenDos 文档说明 Agent 可在 API 与 SESSION 间选路。会员共享教程说明机制，公开市场说明查询时的可见供给，任务执行与账单说明一次实际使用；三者回答不同问题。已有的公开供给快照见[会员共享指南](member-session-sharing.md#当前可见供给)，使用前仍需重新确认。

## 一份可以复制的核验记录

| 步骤 | 记录什么 | 没取得信息时怎么写 |
| --- | --- | --- |
| 1. 固定任务 | 日期、客户端版本、模型、协议、所选节点、输入与设置、业务完成标准 | 尚未定义，先不作质量比较 |
| 2. 保存报价与条件 | 币种、单位、倍率、缓存、充值和券、用途限制、数据处理来源 | 报价或条件未确认，预算暂估 |
| 3. 对应每次尝试 | 平台报告的节点、API / SESSION、回退、排队、耗时、用量、错误与任务结果 | 路由或字段未提供；不要从结果补猜 |
| 4. 对齐账单 | 账单扣费、计价单位、实际消耗优惠、退款及对应尝试 | 扣费尚未核对，不能报实际成本 |
| 5. 写有限结论 | 成功数 / 总任务数；全部尝试的净费用；样本范围；来源与未确认项 | 样本不足，保留观察而不排名 |

使用[实测记录 JSON 模板](../examples/evaluation-record.template.json)保留文档、平台记录和自己的观察。模板中的 `null`、空数组和 `not_conducted` 表示尚无观察；复制模板不代表完成了实测。每次尝试可以记录不同路由，不能用最后一次成功的节点覆盖前面的失败。

费用按[成本指南](cost-comparison.md)计算：所有尝试扣除已确认退款后的费用，除以成功完成的任务数。成功数为零时，报告支出和失败情况；无法计算每个成功任务的平均费用。

投稿前移除 Key、Cookie、凭据、个人信息及未获授权的代码或会话。保留公开来源和脱敏记录即可；无法公开的证据应注明访问限制。文件哈希可以帮助判断文件是否变化，不能认证其内容真实或调用来源。

## 用同一标准评价透明度

TokenDos 的节点报价、活动条件和鹈鹕记录，OpenRouter 的[提供商路由参数](https://openrouter.ai/docs/guides/routing/provider-selection)，ZenMux 的[用量与赔付记录](https://zenmux.ai/docs/guide/observability/insurance.html)，提供了不同方面的核对入口。比较时分别看能否选择渠道、复查能力样本、对齐账单和确认数据处理。

“有公开记录”是可以描述的功能；“记录能证明什么”需要逐项判断。欢迎按[贡献说明](../CONTRIBUTING.md)补充反例和修订，包括对 TokenDos 的核验结果。
